## Fixes

### 1. Add type="button" to ActionButton in message-actions
- **Category**: A11y
- **Files**: `apps/agent/src/components/chat/messages/message-actions.tsx`
- **Commit**: `dc907df`
- **What was wrong**: The `ActionButton` component rendered `<button>` elements without an explicit `type` attribute. Buttons default to `type="submit"`, which can cause unintended form submission if the message actions are ever nested inside a `<form>` context.
- **What I did**: Added `type="button"` to the underlying `<button>` element in ActionButton.

### 2. Add aria-label and type="button" to DiffStatsButton
- **Category**: A11y
- **Files**: `apps/agent/src/components/layout/content-top-bar.tsx`
- **Commit**: `4ce2559`
- **What was wrong**: The `DiffStatsButton` in ContentTopBar had no `aria-label`, making it invisible to screen readers and assistive technology. It also lacked `type="button"`.
- **What I did**: Added `aria-label` sourced from the existing tooltip text (e.g., "3 files changed on branch") and added `type="button"`.

### 3. Remove unsafe `as string` cast in loadImage
- **Category**: Code Quality
- **Files**: `apps/agent/src/lib/utils/image-utils.ts`
- **Commit**: `307b110`
- **What was wrong**: `FileReader.result` has type `string | ArrayBuffer | null` but was cast with `as string` (prohibited by CLAUDE.md). If the FileReader ever returned a non-string result, this would silently produce broken behavior.
- **What I did**: Replaced the unsafe cast with a proper `typeof` guard that rejects the promise with a clear error message when the result is not a string.

### 4. Add type="button" to all tool widget expand/collapse buttons
- **Category**: A11y
- **Files**: 14 files in `apps/agent/src/components/chat/tools/` (bash, code-search, plan, task, write, edit, todo, glob, web-search, browser, read, grep, web-fetch, ask-user-question)
- **Commit**: `c69d505`
- **What was wrong**: Every tool widget's expand/collapse `<button>` lacked an explicit `type="button"` attribute. Only `generic-tool-widget.tsx` already had it. The implicit `type="submit"` default is a latent bug if these widgets are ever rendered inside a form context.
- **What I did**: Added `type="button"` to all 14 tool widget expand/collapse buttons for consistency with `generic-tool-widget.tsx` which already had it correct.

## Logged Issues

### 1. Activity Panel sub-tabs lack per-tab error boundaries
- **Severity**: Medium
- **Category**: Error Handling
- **Files**: `apps/agent/src/components/panels/activity-panel.tsx`, `apps/agent/src/components/files/`, `apps/agent/src/components/git/`, `apps/agent/src/components/browser/`
- **What I found**: The `ActivityPanel` renders three tabs (Editor/File Viewer, Source Control, Browser) but none of them are individually wrapped in error boundaries. A crash in any tab component (e.g., a malformed diff in SourceControlTab, or a browser panel error) would crash the entire ActivityPanel, losing the user's context in all tabs simultaneously.
- **Production impact**: Users with the activity panel open would see a white panel or trigger the top-level mode error boundary, which resets the entire agent mode -- far more disruptive than just the affected tab.
- **Suggested fix**: Wrap each tab content (FileViewer, SourceControlTab, BrowserPanel) in an `<ErrorBoundary>` with a tab-specific fallback that offers a "Retry" button, similar to how App.tsx wraps agent and editor modes.
- **Why not fixed tonight**: Touches multiple files across component boundaries, and the fallback UX (what error message to show per tab) needs product/design input to feel right.

### 2. ConversationItem button missing type="button"
- **Severity**: Low
- **Category**: A11y
- **Files**: `apps/agent/src/components/layout/primary-sidebar/components/ConversationItem.tsx`
- **What I found**: The main `<button>` in `ConversationItem` (line 156) that handles click and double-click for selecting/renaming conversations lacks `type="button"`. While it's not currently inside a form, the editing mode renders a `<form>` sibling, and future refactoring could nest them.
- **Production impact**: Low practical risk today since the button and form are rendered conditionally (never both at once). But it's inconsistent with the convention established in this shift's fixes.
- **Suggested fix**: Add `type="button"` to the conversation item's main button element.
- **Why not fixed tonight**: The component is part of the primary sidebar which has been actively worked on recently (conversation list, vault notes). The code is actively touched and a nightshift change risks conflict.

## Recommendations

- **Systematic `type="button"` audit**: This shift found the pattern in tool widgets and message actions, but a codebase-wide audit would likely find more instances in sidebar components, modal actions, and settings pages. Consider adding an ESLint rule (e.g., `jsx-a11y/button-has-type`) to catch this at lint time going forward.
- **Error boundary coverage map**: The app has error boundaries at the mode level (agent/editor) and on individual message items, but the middle layer (panels, tabs, sidebar sections) is largely unprotected. A systematic pass adding per-panel boundaries would significantly improve resilience for long-running sessions.
- **Tool widget shared button component**: All 15 tool widgets duplicate the same expand/collapse button pattern (className, aria-label, aria-expanded). Extracting a shared `ToolWidgetHeader` component would eliminate this duplication and ensure new widgets automatically get correct accessibility attributes.
