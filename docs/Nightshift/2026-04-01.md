### 8. Add missing .catch() to getSettings() in useGitPolling

- **Category**: Error Handling
- **Files**: `apps/agent/src/hooks/git/use-git-polling.ts`
- **Commit**: `3568428`
- **What I found**: The `useGitPolling` hook calls `getSettings()` via `void getSettings().then(...)` without a `.catch()` handler. If the Tauri IPC call to read settings fails (e.g., corrupted settings file, backend crash), the promise rejects unhandled. The `gitSettings` state stays `null`, which silently disables auto-fetch polling via the `?? true` / `?? 180` defaults in `useAutoFetch` — but the unhandled rejection itself is a runtime error that surfaces in console and could trigger global error handlers.
- **Why it matters**: Unhandled promise rejections are a production error signal. Even though the fallback defaults are safe, the missing `.catch()` means monitoring/error reporting tools flag this as a crash rather than a graceful degradation.
- **What I did**: Added a `.catch()` handler that logs a warning with the error details via the structured logger. The defaults in `useAutoFetch` still apply correctly when `gitSettings` remains `null`.

### 9. Remove prohibited `as unknown as` double cast in tool widget file links

- **Category**: Code Quality
- **Files**: `apps/agent/src/components/chat/tools/write-tool-widget.tsx`, `apps/agent/src/components/chat/tools/edit-tool-widget.tsx`
- **Commit**: `4f1e2e1`
- **What I found**: Both `WriteToolWidget` and `EditToolWidget` have a `handleFileClick` function typed as `(e: React.MouseEvent) => void`, but the keyboard `onKeyDown` handler calls it with `e as unknown as React.MouseEvent` — a prohibited double cast. The handler only uses `e.preventDefault()` and `e.stopPropagation()`, which exist on the base `React.SyntheticEvent` type.
- **Why it matters**: `as unknown as` is explicitly prohibited in CLAUDE.md. The double cast bypasses type safety and masks a simple type mismatch. If `handleFileClick` ever accessed mouse-specific properties (e.g., `clientX`), the keyboard path would silently produce `undefined`.
- **What I did**: Widened `handleFileClick` parameter from `React.MouseEvent` to `React.SyntheticEvent` (the common base type). Both `onClick` (MouseEvent) and `onKeyDown` (KeyboardEvent) extend SyntheticEvent, so both call sites now type-check without any cast.

### 10. Clear LSP workspace ready listeners on initialization failure

- **Category**: Error Handling
- **Files**: `apps/agent/src/hooks/lsp/use-lsp.ts`
- **Commit**: `34e022c`
- **What I found**: The `useLsp` hook uses a module-level `workspaceReadyListeners` Map to coordinate initialization across multiple hook instances. When hook instance A starts initializing a workspace, instance B registers a listener and waits. If `lspSetWorkspace()` fails, the `.catch()` handler sets error state on instance A but never clears or notifies the listeners. Instance B's listener remains in the Map indefinitely — `setIsWorkspaceReady(true)` is never called, so B stays in an unready state with no error feedback.
- **Why it matters**: This is a memory leak and a silent deadlock. Any hook instance waiting on a failed workspace initialization hangs forever with `isWorkspaceReady: false`. LSP features (completions, hover, go-to-definition) stop working for that workspace with no user-visible error. The `cleanupWorkspace()` function does clear listeners, but it only runs when the last hook instance unmounts — not on initialization failure.
- **What I did**: Added `workspaceReadyListeners.delete(rootPath)` in the `.catch()` handler. This clears all waiting listeners for the failed workspace. When those hook instances re-render or remount, they'll see the workspace is neither initialized nor initializing and can re-attempt. The cleanup function's `listeners.delete(onReady)` call from the returned cleanup closure operates on the now-orphaned Set reference, which is harmless (deleting from a detached Set is a no-op on the Map).

### 11. Fix Tauri event listener leak and missing error handling in useFullscreen

- **Category**: Error Handling
- **Files**: `apps/agent/src/hooks/ui/use-fullscreen.ts`
- **Commit**: `2a1aee6`
- **What I found**: The `useFullscreen` hook calls an async `setup()` function that dynamically imports `@tauri-apps/api/webviewWindow`, reads the initial fullscreen state, then registers an `onResized` Tauri event listener. Two problems: (1) `void setup()` had no `.catch()`, so if the dynamic import or any Tauri API call failed, the promise rejected unhandled. (2) The `onResized()` listener assignment to `unlisten` happened asynchronously, but the cleanup function ran synchronously on unmount. If the component unmounted while `onResized()` was still awaiting, `unlisten` was still `undefined`, so cleanup was a no-op and the Tauri listener leaked — it would keep calling `setIsFullscreen` on a stale React state setter.
- **Why it matters**: The listener leak means each mount/unmount cycle of any component using `useFullscreen` (e.g., `ContentCard`) accumulates orphaned Tauri event handlers. In long sessions with layout changes, this could cause measurable overhead from redundant `isFullscreen()` IPC calls on every window resize. The missing `.catch()` is a production error signal — unhandled rejections surface in monitoring tools.
- **What I did**: Replaced fire-and-forget `void setup()` with a stored `pending` promise that captures errors via `.catch()` with structured logging. Rewrote the cleanup function to `void pending.then(() => unlisten?.())` — this waits for the async setup to complete before attempting cleanup, ensuring the listener is always properly removed regardless of timing.

## Logged Issues

### 1. Activity Panel sub-tabs lack per-tab error boundaries

- **Severity**: Medium
- **Category**: Error Handling
- **Files**: `apps/agent/src/components/panels/activity-panel.tsx`, `apps/agent/src/components/files/`, `apps/agent/src/components/git/`, `apps/agent/src/components/browser/`
- **What I found**: The `ActivityPanel` renders three tabs (Editor/File Viewer, Source Control, Browser) but none of them are individually wrapped in error boundaries. A crash in any tab component (e.g., a malformed diff in SourceControlTab, or a browser panel error) would crash the entire ActivityPanel, losing the user's context in all tabs simultaneously.
- **Production impact**: Users with the activity panel open would see a white panel or trigger the top-level mode error boundary, which resets the entire agent mode -- far more disruptive than just the affected tab.
- **Suggested fix**: Wrap each tab content (FileViewer, SourceControlTab, BrowserPanel) in an `<ErrorBoundary>` with a tab-specific fallback that offers a "Retry" button, similar to how App.tsx wraps agent and editor modes.
- **Why not fixed tonight**: Touches multiple files across component boundaries, and the fallback UX (what error message to show per tab) needs product/design input to feel right.

## Recommendations

- **Systematic `type="button"` audit**: This shift found the pattern in tool widgets and message actions, but a codebase-wide audit would likely find more instances in sidebar components, modal actions, and settings pages. Consider adding an ESLint rule (e.g., `jsx-a11y/button-has-type`) to catch this at lint time going forward.
- **Error boundary coverage map**: The app has error boundaries at the mode level (agent/editor) and on individual message items, but the middle layer (panels, tabs, sidebar sections) is largely unprotected. A systematic pass adding per-panel boundaries would significantly improve resilience for long-running sessions.
- **Tool widget shared button component**: All 15 tool widgets duplicate the same expand/collapse button pattern (className, aria-label, aria-expanded). Extracting a shared `ToolWidgetHeader` component would eliminate this duplication and ensure new widgets automatically get correct accessibility attributes.
